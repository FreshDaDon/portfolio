01 Cloud infrastructure

Moodle & AWS migration

Leading the practical deployment of a Moodle environment on AWS, validated through a large-module pilot.

View repository ↗ Private repository · walkthrough on request
Explore case study +

Purpose and objectives

The Moodle & AWS Migration Project was initiated to transition the university’s Learning Management System (LMS) from a third-party hosting arrangement (iLite) to a self-managed cloud infrastructure on Amazon Web Services (AWS). This strategic move was aimed at enhancing system performance, ensuring data sovereignty, optimizing costs, and building internal capacity for managing cloud-based educational technologies.

The project team, comprising internal ICT and CTLPD personnel supported by an AWS partner and external consultant, successfully deployed Moodle on AWS. A comprehensive pilot test was conducted involving a course with over 2,000 students, yielding highly favourable results in terms of stability, scalability, and user experience. The deployment confirmed that AWS infrastructure could meet the university’s academic and operational demands.

Following the successful pilot, the project was paused at institutional level. The AWS instance was decommissioned to avoid ongoing hosting costs; configurations, documentation and performance benchmarks were preserved.

Key functionality

Cloud-hosted Moodle application and database environment.

Storage and content delivery components supporting learning resources.

User access, enrolment and course continuity.

Monitoring, email delivery, security controls and operational support.

Testing and issue resolution across the migrated environment.

My responsibilities and contribution

I led the practical deployment of the Moodle instance on AWS and coordinated the technical activities required to progress from the existing Moodle image and repository to a functioning cloud-hosted environment. My responsibilities included identifying deployment barriers, communicating technical and training requirements to management, completing targeted AWS training, applying the acquired knowledge during deployment and supporting the SCOR pilot. Where specialist input was required, I sought appropriate assistance while retaining responsibility for applying the guidance, resolving implementation issues and validating the resulting environment.

Technical and architectural decisions

Separation of application, database, storage and delivery responsibilities within the AWS architecture.

Use of managed or monitored components to improve reliability and operational visibility.

Consideration of access control, backups, logging, performance and continuity during migration.

Anonymisation of infrastructure details in this portfolio to protect institutional security.

Challenges and achievements

As the only team member with software development experience, I assumed primary responsibility for the technical implementation of the Moodle deployment. Although I had developed foundational AWS knowledge through self-directed learning, I identified specific gaps in my ability to configure and deploy the full environment. I communicated these development needs to my manager and motivated for formal training. This resulted in my attendance at Mecer Inter-Ed online AWS courses, where I strengthened my practical understanding of AWS infrastructure and deployment.

Following the training, I successfully deployed the Moodle instance on AWS, applying the knowledge gained to resolve the earlier deployment challenges. The team validated the environment by piloting it with the Core Curriculum module, SCOR, which had the largest student enrolment and therefore provided an appropriate high-demand test case. The pilot was completed successfully, demonstrating that the deployed environment could support a large module and its associated users, learning resources and activities. This achievement reflects my ability to identify technical limitations, communicate resource requirements, undertake targeted professional development and apply new knowledge to deliver a functioning institutional solution.

Core technologies

Moodle, AWS EC2, RDS PostgreSQL, S3 or EFS, CloudFront, Application Load Balancer, VPC, autoscaling, CloudWatch, SES and WAF.

02 Institutional applications

Tutor Request System

Turning a manual tutor-request process into a structured, auditable Django workflow.

View repository ↗ Live walkthrough available
Explore case study +

Purpose and objectives

The Tutor Request System was developed to replace a largely manual process for requesting and administering tutors. The previous process depended on documents, emails and separate records, which made it difficult to monitor request progress, maintain consistent information and provide stakeholders with a reliable view of outstanding and completed requests.

The objective was to create a centralised, database-backed application through which authorised users could submit tutor requests, review the information provided, move requests through defined approval stages and maintain an auditable record of decisions.

Business problem addressed

The existing process created operational challenges such as incomplete submissions, inconsistent supporting information, limited visibility of request status and difficulty consolidating records for administrative reporting. The system addressed these challenges by standardising data capture and applying a structured workflow to each request.

Key functionality

Secure user authentication.

Electronic submission of tutor requests.

Structured capture of module, staffing and request information.

Server-side validation of required information.

Role-based access to system functions and records.

Controlled review and approval stages.

Request-status tracking.

Filtering and searching of submitted requests.

Administrative oversight of current and historical requests.

Notifications or status communication where applicable.

Database-backed reporting and record management.

My responsibilities and contribution

I contributed directly to the analysis, design and development of the Tutor Request System. I translated the operational requirements of the tutor-request process into a structured digital workflow and implemented the application using Django.

Technical and architectural decisions

I used Django because it provides an established structure for developing secure, database-backed web applications. Its model-view-template architecture allowed me to separate the data layer, processing logic and user interface, thereby improving maintainability.

The application was designed around clearly defined request statuses. A request could only move between permitted stages when the appropriate conditions were satisfied, and the user had the necessary authority. These controls were implemented on the server side so that access restrictions did not depend solely on whether an interface button was visible.

Django models and the object-relational mapper were used to define the application’s data structure and manage database operations. Relationships between users, requests, modules and relevant organisational entities were represented explicitly to support accurate retrieval, filtering and reporting.

Reusable forms and validation rules were used to promote consistent data capture. Where possible, business rules were placed in appropriate model, form or service-level components instead of being duplicated across templates and views.

Core technologies

Python, Django, HTML, CSS, JavaScript, relational database, Django ORM, authentication, role-based access and version control.

03 Institutional applications

Digital Content Studio Booking

Centralising studio reservations with institutional sign-on and server-side scheduling rules.

View repository ↗ Private repository · walkthrough on request
Explore case study +

Purpose and objectives

The Digital Content Studio Booking System was developed to provide lecturers and authorised staff with a structured method for reserving institutional facilities used to produce technology-supported learning materials.

These facilities support activities such as podcast recording, lightboard presentations, video production, live streaming and other digitally mediated teaching activities. The system’s objective was to replace informal booking arrangements with a centralised application that could display availability, capture booking information and assist administrators in managing studio usage.

Business problem addressed

Studio reservations previously depended on manual communication and separate records. This made it difficult to confirm availability, prevent conflicting bookings, maintain complete booking information and monitor how the facilities were being used.

The system addressed these challenges by consolidating booking information within a database-backed application and applying consistent scheduling and validation rules.

Key functionality

Institutional single sign-on authentication.

Selection of the required studio or facility.

Capture of the booking date and time.

Recording of the purpose of the booking.

Availability checking before confirming a reservation.

Prevention of overlapping bookings.

User access to relevant booking information.

Administrative review and management of reservations.

Booking-status tracking where applicable.

Search and filtering by date, studio, user or status.

Historical booking records for operational reporting.

My responsibilities and contribution

I contributed directly to the analysis, design and development of the Studio Booking System. I translated the operational requirements of the digital content studios into a database-backed scheduling application.

My responsibilities included:

Analysing the existing booking process and identifying its limitations.

Gathering requirements from the staff responsible for operating the studios.

Defining the booking information, validation rules and administrative functions.

Designing the application’s database models and relationships.

Developing the Django forms, views, templates and processing logic.

Integrating institutional single sign-on.

Implementing date, time and availability validation.

Developing logic to prevent conflicting reservations.

Testing booking, cancellation and administrative user journeys.

Supporting implementation, documentation and subsequent system improvements.

Technical and architectural decisions

I used Django to provide a structured development framework with integrated support for authentication, database models, forms and security controls. The application separated booking data, business rules and interface components to improve maintainability.

The booking record was designed to associate the user, facility, booking date, start time, end time, purpose and relevant status information. This structure supported availability checking, administrative filtering and historical reporting.

Conflict prevention was implemented as a server-side business rule. Before saving a reservation, the system checked whether another active booking occupied an overlapping period for the selected facility. This ensured that conflicting reservations could not be created by bypassing interface-level restrictions.

The availability logic treated two bookings as overlapping when the proposed start time occurred before an existing booking’s end time and the proposed end time occurred after the existing booking’s start time.

04 Artificial intelligence

Maarifa AI Student Services

Providing source-grounded student support through Retrieval-Augmented Generation.

Architecture and approach documented below
Explore case study +

Problem and purpose: Student-service channels experience increased demand during admissions, registration and examination periods. This can result in delayed responses, repeated enquiries and inconsistent information. I developed Maarifa AI to provide a scalable self-service channel through which students could access approved institutional information.

My contribution: I conceptualised and developed the Maarifa AI solution, including its application architecture, conversational workflow and retrieval-based response process. I structured institutional information for retrieval, implemented the connection between the user interface and AI service, and developed controls intended to keep responses within the approved knowledge base. I also considered privacy, access control, response quality, escalation and future institutional integration requirements.

Key functionality:

Conversational student-support interface.

Retrieval-Augmented Generation using approved institutional information.

Retrieval of relevant content before generating a response.

Source-grounded answers rather than unrestricted model responses.

Handling of unsupported or out-of-scope questions.

Conversation and query processing.

Modular architecture supporting future institutional integrations.

Provision for human escalation when a query cannot be answered reliably.

Design consideration for portal, Moodle and other communication channels.

Technical and architectural decisions: I adopted a Retrieval-Augmented Generation approach because student-services responses needed to be grounded in authoritative institutional information. The solution separated the user interface, application or orchestration logic, retrieval process and language-model interaction. This modular structure supported maintainability and made it possible to update the knowledge base without retraining the language model.

Security and privacy: The project was designed with POPIA considerations, data minimisation and controlled access in mind. The initial solution prioritised general institutional information and avoided unnecessary processing of personally identifiable information.

Technologies: Artificial intelligence, Retrieval-Augmented Generation, large language models, Python, web application development, API integration, document retrieval, prompt engineering, information security and POPIA-aware solution design.
